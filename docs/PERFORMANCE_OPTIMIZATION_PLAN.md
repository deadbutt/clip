# 性能与稳定性优化实施计划

本计划围绕真实任务的耗时、磁盘 I/O、临时文件和批量操作制定。原则是先保留现有转录质量，再减少重复工作；所有优化都必须通过现有测试。

## 已完成

- [x] 记录下载、音频时间轴、Whisper、Demucs、背景检测、说话人标记、翻译、校对和渲染耗时。
- [x] 说话人区间索引，减少字幕段和词级时间戳的重复扫描。
- [x] 进程内媒体 SHA-256 缓存。
- [x] Demucs 背景检测音频复用给 pyannote。
- [x] 背景音 RMS 检测按区间读取，避免长视频整条 16k WAV 一次性载入内存。
- [x] 音频时间轴检测改用 ffprobe 紧凑 CSV 解析，避免为每个包构造 JSON 对象；保留旧 JSON 形状兼容测试和外部调用。
- [x] 媒体库列表缓存，目录变化时自动失效。
- [x] 启动时清理超过一小时的已知孤儿临时文件。

## 本轮实施

- [x] 任务列表响应增加稳定版本标识，减少无变化刷新时的 JSON 传输和序列化。
- [x] 切片导出记录真实耗时和输出字节数，便于定位批量导出瓶颈。
- [x] 任务级临时文件统计写入诊断信息，便于发现异常增长。
- [x] 阶段计时器增加可选 RSS 峰值采样，写入 `job.json.phase_memory_mb` 和 `pipeline.log`；没有 `psutil` 时自动退化为仅计时。
- [x] 阶段计时器仅采样已加载的 PyTorch 分配器，不主动导入 torch；`phase_gpu_memory_mb` 仅表示 PyTorch 采样分配峰值，不覆盖 CTranslate2、FFmpeg 或 llama-server。驱动级测量另见 `tools/benchmark_resources.py`。
- [x] 清理任务临时文件时保留可恢复 checkpoint，避免影响断点恢复。
- [x] 批量切片渲染使用受控并发（最多 2 个 ffmpeg 编码进程），超出任务排队，避免同时导出拖垮磁盘和内存。

## 后续按真实数据实施

- [x] 长视频资源实测：Whisper、Demucs、pyannote 和完整字幕烧录使用约 1059 秒真实视频；翻译使用长任务的真实源字幕；切片使用项目实际字幕烧录函数分别实测 1/2/4 路。原始报告见 `docs/benchmarks/`。
- [x] 统一音频缓存评估：保留任务内修复音频和背景检测 16k WAV 向 pyannote 的复用（修复音频也已接入专用 `audio_path` 参数，跳过二次抽取）；这不等于统一解码。长视频抽取约 3.4 秒，相比 Whisper 149 秒、Demucs 71 秒收益有限，因此暂不增加跨任务 WAV 缓存。Demucs 必须用 44.1k 立体声，不能复用 Whisper 的 16k 单声道输入，避免损伤分离质量。
- [x] 实际烧录函数验证切片并发：4 个 6 秒切片，1/2/4 路分别约 7.63/6.53/6.49 秒，进程树 RSS 峰值约 993/1934/3814 MiB。保留服务器 2 路安全上限；4 路几乎没有额外速度收益。包含启动开销，单次样本不代表所有视频。
- [x] 长视频音频时间轴检测改为ffprobe 输出写入自动清理的临时文件并逐行解析，避免把所有包 JSON/CSV 保存在内存，并用 5 个真实 AAC 样本（0.10–1.69 秒）及无音频封面样本验证：无音频返回 `None`，不会误触发修复。
- [x] 大任务索引评估：100/1000/5000 任务的目录发现耗时约 0.013/0.177/3.063 秒，JSON 加载约 0.028/0.295/4.986 秒；列表使用内存数据。撤销新增的 ID 清单：它不减少 JSON 读取，且目录时间戳不能可靠判定所有外部变化。当前保留目录恢复，暂不引入 SQLite；原始数据见 `docs/benchmarks/jobs-scale.json`。

## 实测记录

- [x] 真实媒体抽样：音频时间轴检测耗时约 0.6–1.7 秒，干净音频和含窟窿音频均能返回结果；未发现该阶段是长视频主要瓶颈。
- [x] 回归验证：后端 336 项通过，前端 Playwright 24 项通过；Ruff 对本轮音频时间轴文件通过。
- [x] 规模测试在系统临时目录中执行，测试完自动清理，未操作正式任务。
- [x] 早期 ultrafast 裸编码仅用作探索；正式结论以上述项目实际烧录函数和 `clips-1/2/4.json` 为准。
- [x] 音频复用检查：任务流程中的 Whisper、Demucs、背景检测和说话人标记均从同一个 `audio_path` 分支取输入；仅 Demucs 输出的人声/背景轨作为后续说话人专用输入，共享的是输入路径，Whisper/Pyannote/Demucs 仍可能分别解码；尚未实现统一解码缓存。
- [x] 早期 84 秒 Whisper 测试耗时约 21.5 秒；当时仅采样 PyTorch，不能据此判断 CTranslate2 的设备。以下驱动级数据替代早期 CPU 判断。
- [x] pyannote 实测：同一约 84 秒真实视频、CPU、本地模型完成 5 段说话人标记约 114.4 秒，RSS 峰值约 3.27 GB，实际识别 3 位说话人。
- [x] Demucs 实测：对真实视频截取 10 秒片段进行一次 CPU 分离，耗时约 8.0 秒、RSS 峰值约 1.96 GB，输出成功；这次显式使用 CPU；不能据此推断本机没有 CUDA。
- [x] OPUS-MT 翻译实测：本地 CPU 模型批量翻译 64 段耗时约 0.6 秒，RSS 峰值约 153 MB。
- [x] 渲染使用实际 `burn_ass_subtitles` 函数（libx264 veryfast，含字幕和音频），完整运行约 17 分钟源视频；使用覆盖全片的一条测试字幕，测试结果不用于评价字幕质量。
- [x] GPU 环境已核实：RTX 4060 Laptop 8GB、PyTorch 2.8.0+cu129 CUDA 可用、CTranslate2 检测到 1 张 CUDA 设备。

## 2026-10-16 驱动级资源实测

使用 `tools/benchmark_resources.py` 隔离运行，正式媒体只读；输出使用系统临时目录，进程退出清理。报告保存在 `docs/benchmarks/`。RSS 统计工作进程及其子进程，每 0.1 秒采样；GPU 每约 0.5 秒通过 nvidia-smi 采样，数值为整卡占用，包含其他程序，不能宣称是单模型的精确显存。

| 阶段 | 输入 | 耗时（秒） | 进程树 RSS 峰值（MiB） | GPU 基线 / 峰值（MiB） |
| --- | --- | ---: | ---: | ---: |
| whisper | 约 1059 秒真实视频 | 149.325 | 2049.4 | 189.0 / 2530.0 |
| demucs | 约 1059 秒真实视频 | 71.302 | 5499.1 | 189.0 / 1108.0 |
| pyannote | 约 1059 秒真实视频 | 59.544 | 1673.2 | 189.0 / 1066.0 |
| OPUS-MT | 长任务的真实源字幕 | 51.02 | 786.7 | 189.0 / 510.0 |

- pyannote 扫描完整音频，提供 5 个字幕段用于验证返回；未用此测试评价完整字幕说话人质量。
- OPUS-MT 使用真实源字幕；这些结果不代表 HY-MT2 或远端 AI 翻译性能。
- 修复翻译冷启动时 CUDA DLL 尚未注册的问题，避免依赖先运行 Whisper 或意外回退 CPU；修复后明确指定 CUDA 完成上述测试。
- Demucs 计时移动到执行线程内部，去掉等待 Whisper 带来的虚高耗时，并接入阶段 RSS/PyTorch 采样。并行阶段的采样值是共享进程占用，不能相加当成模型独立用量。
- CSV 临时文件逐行路径与旧 JSON 路径已在现有 12 个 MP4/MKV 样本（10 个含音频，2 个无音频）上对照，结果全部相同（含 66 处窟窿的媒体和无音频媒体）；耗时约 0.05–2.65 秒。

完整字幕烧录首次记录：535.019 秒，进程树 RSS 采样峰值 1093.0 MiB。该次为 CPU libx264；GPU 峰值 510.0 MiB 包含同时运行的翻译和桌面占用，不能归因于渲染。该次存在并行负载，不作为独占烧录性能基准。
