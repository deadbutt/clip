# 转录与说话人标记性能排查报告

日期：2026-09-17。原则：质量优先，不以降低识别、词级时间戳或说话人归属质量换取速度。

**最新实测更正：** 按日常启动参数从真实网页上传同一素材，当前优化版转录201.7秒、说话人加载与标记51.2秒，从点击开始到待校对276.4秒（4分36秒）。相同自动语言参数的后台直跑处理时间与网页一致（269.1 vs 268.1秒，不含网页上传）。早期159.99秒是另一轮实验成绩，本轮未复现；不能用它估算日常优化后只需144～146秒。详见第10节。

## 结论与建议顺序

**最值得优化的是 pyannote 的重复声纹计算：同一音频窗口的特征和卷积输出可以共享，仅对不同说话人掩码分别计算后面的聚合。** 早期实验中说话人推理约快2.4倍，正式集成对照为1.4～1.6倍，三份素材的原始说话人轮次均完全一致。这是局部推理加速，不是全流程提速倍数，也不意味着说话人人数判断已经正确。

| 优先级 | 方向 | 证据/收益 | 质量与落地条件 |
| --- | --- | --- | --- |
| 1 | 共享同一窗口的声纹前部计算 | 排查实验中22.75分钟素材约44.5～47.4 → 18.6～19.3秒；正式集成结果见第9节 | 已接入受兼容检查保护的正式路径；保留原音频、全部窗口和掩码，并提供回退开关 |
| 2 | 复用已计算的音频分段/声纹特征，只重做人数聚类 | 当前指定人数不足时可能重跑整个模型；这类重试可避免重复网络推理 | 仅对同一音频、同一模型和参数复用；本轮自动人数任务未触发该分支，未测得实际节省量 |
| 3 | 串行 Demucs 路径先做原有背景音判断 | 目前先完整分离，再判断不用分离结果；无 BGM 时可省整次分离 | 必须使用同一词表、音频和原判断规则；有 BGM 的本轮素材无此收益；不把新检测器等同于原规则 |
| 4 | 首次依赖导入预热 | 首次 pyannote 加载约 14～16 秒，主要为模块导入 | 只能把首次等待提前或重叠，不能宣称减少持续计算量；会增加启动工作量 |
| 低 | 调整 batch、缓存 pipeline、重复解码、字幕匹配 | 已测，收益小或未出现稳定提速 | 不作为当前主线 |
| 暂不启用 | 降 beam、量化、删缺口恢复、裁掉非 ASR 区域、换批量解码路径 | 会改变识别行为，尚未满足质量要求 | 不能因“通常影响小”直接上线 |

最初排查阶段仅保留报告；用户随后授权实施，已接入第1项优化，修改范围及正式验收见第9节。文中“已验证”仅限列出的素材与配置，不能代替更多素材的质量回归。

## 2. 最大机会：共享重复窗口的声纹网络计算

### 现状与原因

pyannote 的 `get_embeddings` 对每个时间窗口的每个局部说话人分别产生一条“波形 + 掩码”。本机的 WeSpeaker 实现先计算完整波形的 fbank 和 ResNet 特征，最后才使用掩码做统计聚合。

同一窗口的波形因而被重复计算。主素材共有 **4071条输入**，其中 **2629条是批次内相邻重复波形**；保留原 batch 边界后，前部实际只需计算1442条。没有删除任何静音、背景音乐、短插话或说话人掩码。

原路径分解：声纹调用墙钟约43.05秒；GPU event统计中，fbank约1.204秒，ResNet约41.571秒。主要瓶颈在卷积计算，不在CPU裁剪或音频读取。

### 实验实现

在单次 batch 内只合并**波形逐元素完全相同的相邻条目**，通过现有 `forward_frames` 计算一次前部特征，再按逆映射恢复原条目顺序，通过 `forward_embedding` 使用每条原始掩码完成聚合。保持模型权重、精度、全部窗口和后续聚类规则不变。实验代码只在独立进程生效。

| 素材/方式 | 基线说话人推理 | 共享前部计算 | 轮次输出 | 最大声纹绝对差 |
| --- | ---: | ---: | --- | ---: |
| 22.75分钟，人声轨，首次 | 47.393秒（含profiling） | 19.284秒 | 完全一致，352条 | 6.26×10⁻⁷ |
| 同一素材复测 | 44.527秒 | 18.630秒 | 完全一致，352条 | 6.26×10⁻⁷ |
| 17.65分钟，原音轨 | 34.327秒 | 13.967秒 | 完全一致，361条 | 0 |
| 5.825分钟，原音轨 | 11.333秒 | 4.494秒 | 完全一致，87条 | 0 |

主素材去重检查自身约0.29～0.33秒，已包含在加速耗时中。PyTorch推理峰值分配从约1629 MiB降到636 MiB；这不是整机显存用量，不包含其他框架/进程占用。

### 质量边界与落地建议

该优化在数学结构上复用同一计算，但减少 batch 条目可能改变CUDA计算顺序，所以主素材出现微小浮点差异。当前三份素材的最终原始轮次完全一致，另外两份连声纹向量也完全一致。仍不能由三个样本证明所有聚类边界都不会变化。

据此选择进入正式开发，限定到已验证的 WeSpeaker eval 路径；不支持的声纹模型继续原路径。应继续增加快速抢话、相似音色、极短插话和临界聚类素材验证，并保留回退开关。此处全流程潜在节省约25秒来自排查素材的局部阶段差额，不是集成后完整流水线实测，不能直接宣传成全流程2.4倍。

## 5. 缺口恢复与小环节

本轮每次检测到42个缺口，42次局部重试补出78个词、30个原始段。检测前的缺口数不能从已经补录完的历史词表倒推。

| 环节 | 测得耗时/结论 |
| --- | --- |
| 缺口恢复总计 | 20.57～22.46秒 |
| 其中局部重转录 | 19.70～21.36秒 |
| 读取缺口检测音频 | 0.086～0.093秒 |
| 其余检查/临时文件等合计 | 约0.86～2.06秒，含测量与调用开销 |
| 音频时间轴检查与修复 | 1.53～1.86秒 |
| 背景音检测 | 0.29～0.55秒 |
| 词与说话人轮次匹配 | 0.13～0.14秒 |

因此不删除缺口恢复，不把总耗时当成“重复解码浪费”。新增词是否正确需要听音核验，性能实验保持原规则。全片低覆盖率触发的无VAD重试是另一个潜在大开销，但本轮没有触发，不能报出优化收益；更精确地改变触发条件也必须验收漏词风险。

背景音门控目前位于分离完成后。串行路径可以用同一词表、同一判断规则先判断是否采用人声轨；在最终本来会丢弃人声轨的任务里可省掉分离。并行路径若等ASR完成后再判断，会丢失原本的重叠时间，必须另外权衡，不能统一前移。中途恢复任务也应使用checkpoint词表，避免因传入空词表保守启用分离。

## 6. batch与其他改变推理行为的选项

声纹batch 16/32/64分别约47.93/44.53/46.44秒，单次对照未看到64提速；推理峰值分配约834/1629/3218 MiB。轮次一致，但batch32当前已合理，没有必要盲目调大。

Whisper的批量路径已静态确认会关闭 `condition_on_previous_text` 并禁用原 `hallucination_silence_threshold`，还会改变切块与回退行为。它不是无损开关；本轮不把常见的2～3倍外部成绩当成本项目实测，不以它替换质量优先路径。

beam 5→3、INT8/FP16变化、TF32、混合精度、裁剪ASR未覆盖音频、减少Demucs重叠或随机位移，都不属于已证明无质量变化的优化。用户已明确质量优先，暂不建议默认启用。

现有 runner 已缓存Whisper模型；`max_new_tokens`、`decoding`、`temperature`等入口参数在当前runner中被忽略，调这些不能加速。安装Python的 `flash-attn` 不会自动加速CTranslate2，必须使用后者自己的接口并检查词对齐兼容性。

## 10. 按网页实际操作复现耗时差异

### 方法与适用范围

用户指出日常转录约3分钟、说话人标记近1分钟，与之前引用的159.99秒总耗时不符。因此在本机顺序运行三个新进程、新任务，均保留已实施的声纹优化，不使用转录checkpoint。

两轮网页测试均通过Chrome无头自动化加载真实前端、上传完整视频、选择auto说话人、保留自动人数、点击“全部开始转写”、保持任务页打开。未使用模拟API。服务使用生产 `web_cli.main → create_app → JobManager`，参数与当前start.bat一致，运行库和本地模型相同。仅将任务输出定向到根目录下独立 `.perf-web-runs`，继续读取相同 `config/hotwords.json`。第三轮同样构建生产应用，但不启动HTTP服务、不打开网页，直接向JobManager提交同一素材，用于隔离网页入口和事件推送影响。

新增计时仅在独立诊断进程内包装函数，记录加载、主转录、稀疏检查、缺口补录、Demucs、说话人阶段和状态回调。不改变生产代码、阈值或模型权重。nvidia-smi约每秒采样一次，三个GPU任务不并行。没有调整电源、驱动、显卡或厂商设置。用户明确说明平常插电、正常性能模式，没有开节能；系统查询电池状态也报告接通电源。

### 已确认的原因与已排除的解释

**1. 网页入口没有解释约100秒的差距。** 自动语言两轮的后台总耗时268.1/269.1秒，词表及词时间戳逐项完全一致（2997词）。状态回调均不足0.3秒。当前后台直跑也没有复现早期160秒成绩；这支持“旧实验与当前运行条件不可直接比较”，而不是“绕过网页就能快很多”。单次顺序实验存在运行波动，不能据此宣称网页绝对零开销。

**2. 启动脚本的英语设置没有真正传入程序，重复语言检测有直接计时证据。** start.bat设置了 `WHISPER_LANGUAGE=en`，但没有传递 `--language`，程序也未读取该环境变量，故实际language=null。原先记录英语的实验与日常默认不是同一语言配置。本轮自动模式每次缺口补录都重新检测语言：主转录1次＋缺口42次；第三轮检测累计26.710秒，其中缺口检测25.411秒。41次检测为英语，另各1次为法语、日语，出现在短补录片段。

指定英语后，缺口恢复从69.1秒降到49.5秒，但同期主转录从132.5秒变成150.7秒，整段转录仅快1.3秒。因此可以确认重复检测是开销，却不能把这两个非同速轮次的局部差额当成稳定总收益。自动语言补79词、固定英语补78词，输出并非完全相同；本次仅诊断，没有擅自把所有素材默认强制英语。

**3. 当前GPU执行状态与早期快成绩不具可比证据。** 主转录和Demucs均明显慢于早期：早期并行4的主转录73.09秒、Demucs40.90秒；本轮主转录132～151秒、Demucs76～90秒。三轮Whisper期间利用率≥80%的样本中，SM频率中位数依次915/825/855MHz，功耗中位数19.08/18.39/18.60W。网页en轮135个繁忙样本中133个同时报告 `SW Power Cap`、`SW Thermal Slowdown`；后台轮140个繁忙样本全部报告这两个标志。网页auto轮的周期采样未包含标志字段，但额外的运行中详细快照报告两者Active。

本轮采样温度最高54～55℃，详细快照的硬件热降频与硬件power-brake为Not Active，目标温度显示87℃。这些是**驱动报告的限制标志和低频实测**，不能直接等同于用户开了节能模式，也不能仅因“Thermal”字样断言散热过热。平台、电源分配、驱动或传感器/策略来源尚未定位；没有依据将全部剩余差额量化归因到某一种限制。历史原始实验日志已按此前要求清理，报告未保存同口径频率/功耗序列，无法证明两轮相差多少MHz、其因果贡献是多少。

**4. 不是加载模型、整片漏词重跑、素材换小了或CPU回退。** 三轮主转录均只有1次，稀疏检查均false；42次缺口补录均执行，主结果均2918词/500原始段。模型加载约6～7秒且不计入转录elapsed；输入哈希相同；实际CUDA FP16已验证。历史3013词与本轮2997/2996词的差异不能用速度数字解释成质量改善。

### 结论与后续边界

当前条件下，日常网页完整处理该22.75分钟素材约 **4分30秒上下**，本轮自动语言从点击到完成为 **4分36秒**。这已经包含声纹优化。此前“优化后约144～146秒”的推算撤回；声纹优化收益应引用第9节的同条件对照，不能用跨轮总耗时相减代替。

已找到约25秒重复短片段语言检测开销，并排除了网页入口导致大幅变慢的解释；GPU运行状态有明确限制线索，但**历史160秒与当前268秒之间的完整根因尚未完全定位**。下一步若继续查，应在相同电源/驱动/厂商性能状态下保持同素材同参数，配合频率、功耗及阶段计时做可重复对照，而不是直接改beam、删补录或强制英语。

本轮没有修改生产启动方式或识别规则。诊断服务均在任务结束后退出，仅使用独立目录，原5个任务保留。测试脚本、上传副本、临时音频、截图和原始日志按此前清理要求移除，共51个文件、2,674,269,959字节（约2.67GB）；两个独立诊断目录均已确认不存在。关键条件、结果及限制保留在本节。
